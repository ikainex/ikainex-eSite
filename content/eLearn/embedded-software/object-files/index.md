  - id: "compile-stages"

    dialogue:

        text: "What happens between my blink.c file and blink.o?"
      - speaker: "Ved"

      question: "Which stage turns assembly instructions into a relocatable .o file?"

  - id: "elf-sections"
    navTitle: "ELF sections"
    kicker: "SORTED INTO SECTIONS"
    title: "Where do the LED instructions and variables live?"
    dialogue:
      - speaker: "Parth"
        emotion: "curious"
        text: "My function, initialized counter, and constant LED mask are all in blink.o. How can I tell them apart?"
      - speaker: "Ved"
        emotion: "demonstrating"
        text: "**.text** holds instructions; **.data** holds initialized writable values; **.bss** reserves zero-initialized writable values; and **.rodata** usually holds constants. Think of these as labeled bins in the object file."
      - speaker: "Parth"
        emotion: "thinking"
        text: "Does the .bss section store a long run of zero bytes in the object?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "Usually it records the space to reserve rather than storing all those zeros in the file. Startup code later clears that RAM region. Use **objdump -h** or **readelf -S** to inspect section names and sizes."
    quiz:
      question: "A writable global counter starts at zero. Which section commonly reserves its storage?"
      answer: ".bss. It reserves space for zero-initialized data that startup code clears."
  - id: "symbols-relocations"
    navTitle: "Symbols & relocations"
    kicker: "WHAT THE LINKER STILL NEEDS"
    title: "Why does the object keep unresolved addresses?"
    dialogue:
      - speaker: "Parth"
        emotion: "confused"
        text: "The blink function calls delay_ms(), which lives in another file. How does this object know its address?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "It doesn't yet. The symbol table records names defined here and names that are still undefined. A relocation entry marks a location the linker must patch once it knows the final address."
      - speaker: "Parth"
        emotion: "thinking"
        text: "So I can inspect the names with nm and the patches with readelf?"
      - speaker: "Ved"
        emotion: "encouraging"
        text: "Yes. Try **nm blink.o** for symbols, **readelf -s blink.o** for symbol details, and **readelf -r blink.o** for relocation entries."
    quiz:
      question: "What does a relocation entry tell the linker?"
      answer: "It identifies a location that needs an address-dependent fix-up when final symbol addresses and placement are known."
  - id: "inspect-object"
    navTitle: "Inspect the object"
    kicker: "TOOLS YOU CAN USE TODAY"
    title: "How do we verify the blink build?"
    dialogue:
      - speaker: "Parth"
        emotion: "curious"

      - speaker: "Ved"
        emotion: "demonstrating"
        text: "Use **objdump -d blink.o** to disassemble its instructions and **objdump -t blink.o** to inspect symbols. **readelf -S blink.o** lists sections, while **nm -u blink.o** shows unresolved references."
      - speaker: "Parth"
        emotion: "thinking"
        text: "If the GPIO helper is undefined, did the compiler fail?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "Not necessarily. Another source file or library may provide it at link time. First check the build includes that provider; then inspect the final link map if resolution still fails."
    takeaway: "A .o file is a relocatable ELF building block: sections organize code and data, symbols name definitions and references, and relocations tell the linker what to fix."
