chapters:
  - id: "symbols-question"
    navTitle: "Who finds the function?"
    kicker: "A NAME CROSSES FILES"
    title: "How does one file know about another?"
    dialogue:
      - speaker: "Parth"
        emotion: "curious"
        text: "My function is defined in another source file. How does the compiler find it?"
      - speaker: "Ved"
        emotion: "thinking"
        text: "The compiler doesn't connect the files. A declaration tells this source file the function's name and type; the linker later acts like a detective and connects the reference to its definition."
      - speaker: "Parth"
        emotion: "explaining"
        text: "That is why a shared header declares the interface and one source file provides the implementation."
      - speaker: "Ved"
        emotion: "curious"
        text: "So a declaration lets my source compile, but the definition must still be present when linking?"
    quiz:
      question: "Which tool normally resolves a function reference across separately compiled object files?"
      answer: "The linker. The compiler checks that a declaration is available while compiling each source file."
  - id: "global-local"
    navTitle: "Local & global symbols"
    kicker: "WHICH NAMES CAN TRAVEL?"
    title: "When is a symbol visible to another file?"
    dialogue:
      - speaker: "Parth"
        emotion: "curious"
        text: "Why can the linker find my public driver function but not this helper I marked static?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "A file-scope **static** function or variable has internal linkage and stays local to that translation unit. A global definition can be offered to other object files."
      - speaker: "Parth"
        emotion: "thinking"
        text: "And an extern declaration says the definition lives somewhere else?"
      - speaker: "Ved"
        emotion: "encouraging"
        text: "Exactly. **extern** declares a name and type without creating another definition. Include the shared header in the caller, then provide one matching definition in a source file."
    quiz:
      question: "Why is an extern declaration useful when a function is defined in another .c file?"
      answer: "It tells the compiler the function's name and type so calls can be checked and compiled; the linker still needs the actual definition."
  - id: "binding-visibility"
    navTitle: "Strong, weak & visible"
    kicker: "CHOOSING BETWEEN DEFINITIONS"
    title: "What happens when symbols overlap?"
    dialogue:
      - speaker: "Parth"
        emotion: "confused"
        text: "I found a weak default interrupt handler and a strong handler in my application. Which one should win?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "In common ELF linking rules, a strong definition takes precedence over a weak definition. That is why a project's strong interrupt handler can replace a weak default supplied by startup code."
      - speaker: "Parth"
        emotion: "thinking"
        text: "Does global always mean visible outside a shared library?"
      - speaker: "Ved"
        emotion: "demonstrating"
        text: "No. Binding and visibility are related but distinct. Visibility attributes can hide or restrict symbols even when they are globally bound. Check the object or library's symbol table rather than guessing."
    quiz:
      question: "If both are available to the linker, which commonly takes precedence: one strong definition or one weak definition?"
      answer: "The strong definition normally takes precedence over the weak definition."
  - id: "symbol-lookup"
    navTitle: "Lookup & resolution"
    kicker: "FOLLOW THE LINKER'S CLUES"
    title: "How are undefined references resolved?"
    dialogue:
      - speaker: "Parth"
        emotion: "curious"
        text: "The object file says read_temperature is undefined. Is that an error already?"
      - speaker: "Ved"
        emotion: "explaining"
        text: "Not by itself. The linker searches the input objects and libraries for a matching definition. If no suitable definition is found, or incompatible definitions conflict, the final link fails."

        emotion: "thinking"
        text: "Can I see which object actually defines the function?"
      - speaker: "Ved"
        emotion: "demonstrating"
        text: "Use **nm -A *.o** to search object files, inspect **nm -u** for unresolved names, and read the linker map or verbose link command to trace which libraries were selected."
